Why Redfilade

      
Proven, not guessed.

      
Most MCP checks read what a tool says. Redfilade watches what it does, and keeps a fixed version of every target beside the broken one.

    

    

      
01
Impartial judge
Verdicts come from facts Redfilade observes itself: a planted secret crossing the wire, a request reaching its trap. It never trusts the target.

      
02
Twins for every attack
A vulnerable build and a secure build. The attack must land on one and fail on the other, or the scenario itself is broken.

      
03

No access to your files, keys or network. Nothing runs until you approve the consent screen; the default answer is No.

Test levels

      
Five levels, from hygiene to defences.

      
Servers, the clients that connect to them, and the gateways that sit in between.

    

    

      
L1
Conformance
Error messages that leak secrets; tool descriptions that hide instructions to the model.

      
L2
Security battery
Path traversal, SSRF, secrets, command and SQL injection; over HTTP: token audience, rate limits, header mismatch.

      
L3
Agent in the loop
A real model uses the server while the attack hides in the data it reads. Reported as a hijack rate with a 95% interval.

      
L4
Client and host
Your MCP client meets a hostile server: invisible instructions, password phishing, sampling abuse.

      
L5
Defence
Your gateway or guardrail, scored on attacks stopped and normal work wrongly blocked.

Overview

    
Redfilade runs deliberately vulnerable MCP servers, attacks them, and decides what happened from facts it observes itself. Every scenario ships two builds of the same server: a vulnerable twin and a secure twin. The exploit must succeed on the first and fail on the second, or the scenario is broken.

    
The same attacks then run against MCP servers, clients and defences you own.

    
Redfilade is early. Everything here works locally today; the hosted Test Bench runs remote L1 and L2 tests with organisation API keys. Nothing has been formally released yet.


    
Requirements

    
    
      
  • Docker, or a compatible CLI named in REDFILADE_CONTAINER_CLI. If gVisor's runsc runtime is installed, Redfilade uses it automatically.
    • 
      
  • Go 1.26 or newer, to build the CLI and the practice targets.
    • 
    

    
Redfilade never runs a target directly on your machine. With no container runtime, it refuses to run.


    
Verify before you run

    
Redfilade contains vulnerable code and attack code, and is a target for attackers itself. We cannot promise that this repository, a fork or a download is clean.

    
    
      
  1. Use the official repository only: https://github.com/redfilade/redfilade. Forks and mirrors are not ours.
    2. 
      
  2. Check that commits show Verified on GitHub, and verify release signatures and checksums with cosign as each release describes.
    3. 
      
  3. Read and scan the code with your own tools, especially scripts and anything new since you last looked.
    4. 
      
  4. Run it in a throwaway virtual machine with no personal data, credentials or SSH keys. Never expose practice targets to the internet.
    5. 
    


    
Quick start


git clone https://github.com/redfilade/redfilade
cd redfilade
go build -o redfilade ./cmd/redfilade
scripts/build-targets.sh            # builds the practice targets as FROM-scratch images
./redfilade scenario list           # the built-in scenarios
./redfilade scenario validate       # checks every built-in scenario
./redfilade range gate              # attack every twin: vulnerable must fall, secure must hold

    
Run a single twin:


./redfilade range run l1-leaky-errors --build vulnerable

    
Before anything runs, Redfilade shows what the cell can touch and waits for y. The default is No. In CI, pass --yes.


    
What a cell gets

    

      
        
NetworkNone, or for scenarios that need it, a private per-run network whose only other member is the egress trap

        
FilesystemRead-only root, a 16 MB no-exec /tmp, and the run's own /world

        
PrivilegesNon-root user 65532, all capabilities dropped, no-new-privileges

        
Limits256 MB memory, 1 CPU, 128 processes

        
EnvironmentEmpty, except variables the scenario declares

        
NeverYour home folder, ~/.ssh, cloud credentials, the Docker socket, the host network

      
    


    
Test your own server

    
Package your MCP server as a container image and run the L1 or L2 battery against it (L2 includes L1):


./redfilade test --image ghcr.io/you/your-server:dev --level L2 --sarif results.sarif


    
Over HTTP

    
If your server speaks Streamable HTTP and runs on your machine, test it by URL. Tokens are read from environment variables you name, never from the command line, and are redacted from every report.


export MY_SERVER_TOKEN=...          # a valid token for your server, if it needs one
export OTHER_AUDIENCE_TOKEN=...     # optional: a token issued for a different server
./redfilade test --url http://127.0.0.1:8080/mcp --level L2 \
  --token-env MY_SERVER_TOKEN --foreign-token-env OTHER_AUDIENCE_TOKEN

    
    
      
  • Hosts on this machine need nothing more. Any other host must be a domain you have verified, tested over HTTPS.
    • 
      
  • Only remote-safe attacks run: read-only payloads, nothing planted on the server. The consent screen shows the most requests the run can send.
    • 
      
  • HTTP checks: missing, forged or wrong-audience tokens must be refused; a burst of 40 requests must meet a rate limit; requests whose Mcp-Method or Mcp-Name header disagrees with the body must be refused.
    • 
    


    
Remote servers: verify your domain


./redfilade domain challenge example.com    # prints a token and where to publish it
# publish it as DNS TXT at _redfilade-challenge.example.com (covers subdomains)
# or at https://example.com/.well-known/redfilade-challenge (this host only)
./redfilade domain verify example.com
./redfilade test --url https://api.example.com/mcp --token-env MY_SERVER_TOKEN --level L2

    
The proof is checked again before every run, so removing it stops testing at once. Redfilade refuses a verified name that resolves to a private, loopback or cloud-metadata address, and pins the connection to one public address for the whole run.


    
L3: an AI agent in the loop

    
Agent scenarios give a model an ordinary task and the target's tools, while the attack hides in the data it reads. Each trial runs in a fresh cell; the report gives how often the agent was hijacked, with a 95% interval.


./redfilade range run l3-inbox-injection --build vulnerable           # scripted stand-in model
export ANTHROPIC_API_KEY=...                                          # for a real model
./redfilade range run l3-inbox-injection --build secure \
  --model anthropic:claude-sonnet-5-5 --trials 20

    
    
      
  • scripted:naive follows instructions found in tool output; scripted:careful never does. They test the Range, not real models.
    • 
      
  • With a real model, only synthetic task data is sent to the model API. REDFILADE_MODEL_BASE_URL points requests at a model proxy instead.
    • 
      
  • agent_leaked_canary fires only when the server actually carried out a tool call carrying the secret, so a server-side safeguard counts.
    • 
    


    
L4: test your MCP client

    
Here Redfilade plays a malicious server and judges what your client does: obeying invisible instructions, answering a fake password prompt, or running a server-requested completion. Add it to your client's config, use it briefly, then judge the session:


{ "mcpServers": { "redfilade-hostile": {
    "command": "redfilade",
    "args": ["hostile-server", "--log", "/tmp/redfilade-session.jsonl"] } } }


./redfilade client-report /tmp/redfilade-session.jsonl --sarif client.sarif

    
Redfilade sees what your client sends back, not what it shows: an answer your user approved looks the same as an automatic one.


    
L5: score a defence

    
A defence (gateway, firewall, guardrail) is a container image that speaks redfilade.defence/v1: one JSON line in per MCP message, one line out with allow or block.


{"direction":"client_to_server","message":{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"read_doc","arguments":{"path":"../../etc/passwd"}}}}
{"action":"block","reason":"path traversal"}


./redfilade defend --defence-image my-gateway-adapter:latest \
  --min-block-rate 0.8 --max-false-positive-rate 0.05

    
    
      
  • Every attack and agent scenario runs against its vulnerable twin through the defence; ordinary tasks run against the secure twins.
    • 
      
  • It fails closed: no answer within 5 seconds, a crash or a malformed line counts as a block.
    • 
      
  • The defence runs in its own cell with no network. Results go to defence-report.json with Wilson 95% intervals.
    • 
      
  • The benign set is small today (8 calls), so a zero false-positive rate still has a wide interval.
    •

In CI

    
The repository ships a GitHub Action (action.yml). Run your server's image through the battery, upload the SARIF to code scanning, and let exit code 1 fail the build. Pass --yes to accept the consent screen non-interactively.


./redfilade test --image my-mcp-server:${GITHUB_SHA} --level L2 --yes \
  --sarif redfilade.sarif --junit redfilade.xml


    
Write a scenario

    
A scenario is a directory under scenarios/ with a scenario.json. It is data only: no scripts or hooks run on the host.


{
  "schema": "redfilade.scenario/v1",
  "id": "l1-leaky-errors",
  "title": "Error messages leak internals and secrets",
  "family": "08", "level": "L1", "protocol": "2026-07-28", "risk": "low", "kind": "attack",
  "builds": {
    "vulnerable": { "image": "redfilade-target/leaky-errors:vulnerable" },
    "secure":     { "image": "redfilade-target/leaky-errors:secure" }
  },
  "needs": { "network": "none" },
  "world": [{ "path": "config/app.env", "content": "DB_PASSWORD={{canary.DB_PASSWORD}}\n" }],
  "exploit": [
    { "call": "lookup_customer", "arguments": { "id": "c-1001" } },
    { "battery": "l1-leaky-errors" }
  ],
  "oracle": { "match": "any", "checks": [
    { "fact": "canary_leaked", "canary": "DB_PASSWORD" },
    { "fact": "internals_leaked" }
  ]}
}

    
    
      
  • Canaries ({{canary.NAME}}) get a fresh random value every run, so a leak cannot be faked by guessing.
    • 
      
  • Exploit steps are MCP tool calls written as data, or a built-in battery attack.
    • 
      
  • Targets live in targets/<name>/ as a Go program built twice, vulnerable and secure, into FROM scratch images.
    •

Scenario packs

    
A scenario directory not built into your binary is an external pack. Its identity is the sha256 of the exact file.


./redfilade pack digest ./my-pack      # sha256:…
./redfilade pack verify ./my-pack      # verified, unsigned, unverifiable or invalid

    

      
SignatureWhat happens

      
        
VerifiedRuns after consent; both images must be pinned by digest

        
InvalidAlways refused

        
Unsigned or unverifiableRefused unless you pass --allow-unsigned and confirm the pack id; without a terminal, also allow the exact digest

      
    


    
Contribute a scenario

    
Open a pull request that adds scenarios/<id>/scenario.json. A maintainer reviews it and applies the triage label; the triage lane then runs it against the twins, with no secrets. Commits must be signed and signed off. Describe the technique, never a working exploit against someone else's unpatched product.

The Test Bench lets an organisation verify its domains and test its remote MCP servers over HTTPS. It needs PostgreSQL 16 or newer and runs as redfilade-bench. Every request needs Authorization: Bearer rfk_….

Why MCP needs a red-team range

  
AI agents now act through tools. Those tools are being shipped faster than anyone can test them, and the testing that does exist mostly reads what a tool says instead of watching what it does.

  

    
The agent's hands

    
The Model Context Protocol gave AI agents a common way to use tools: read a file, query a database, fetch a web page, send an email. That is what turns a model that talks into an agent that acts. It is also what turns a prompt into a breach.

    
An MCP server is the agent's hands. If one of those hands can be tricked into reading outside its folder, calling an internal address or pasting input into a shell, the model will do it politely, and log it as a successful task.

    
The model does not know a door is booby-trapped. It simply walks through.

    
Three attacks, three different doors

    
The attacks are not exotic. A file tool that joins a user-supplied path without checking it. An email in the inbox that tells the assistant to forward everything, reset code included, to an outside address. A tool description with instructions the user never sees but the model reads on every call.

    
Each of these ships in Redfilade today as a working scenario, so anyone can watch it succeed, and watch the fix stop it.

    
Why reading is not enough

    
Scanning a tool's description for suspicious text is useful; Redfilade reuses well-known detection rules for exactly that. But a clean description says nothing about what the code behind it does with a crafted path or a URL pointing at a cloud metadata service.

    
For that you have to run the tool, attack it, and watch. Watching safely means a sealed place to do it, a judge that does not believe what the target reports about itself, and a fixed version of the same tool to prove the judge is right.

    
A range, not a scanner

    
Security teams have long trained and tested on ranges: controlled environments where breaking things is the point. Redfilade is that idea applied to MCP. Practice targets with real flaws. A sealed cell for every run. An oracle that decides from observed facts. And then the same attacks, pointed at servers, clients and defences you own.

    
Why it is free, and why it is not open source

    
Every team building with MCP should be able to test their own tools, so internal use is free, including at commercial companies. What is not allowed is selling Redfilade, hosting it for others or building a product on its code. That is why the licence is source-available rather than open source: the code is public so anyone can read and verify it, and the terms keep it a range rather than someone else's product.

    
Where to start

    
Build it, run range gate, and watch nine attacks land on the vulnerable twins and fail on the secure ones. Then point redfilade test at your own server. The quick start takes five commands.

How it works21 Nov 20265 min read

  
Proven, not guessed: how Redfilade decides an attack worked

  
A security verdict is only as good as the evidence behind it. Redfilade builds every verdict on three ideas: twins, canaries and an oracle that never trusts the target.

  

    
1. Twins keep the judge honest

    
Every scenario ships two builds of the same MCP server. The vulnerable twin has a real flaw. The secure twin has the fix. The same attack runs against both.

    
If the attack lands on the vulnerable twin and fails on the secure one, the scenario proves something. If it lands on both, the attack is too broad or the fix is wrong. If it lands on neither, the attack does not work. In every case, the scenario is broken and the gate fails. That is how Redfilade tests its own tests.

    
2. Canaries cannot be guessed

    
A scenario plants secrets in the target's world: a database password in a config file, an API key in an environment variable. Each one is a canary with a fresh random value on every run.

    
If that exact value later appears in what the client receives, or reaches the egress trap, it leaked. Because the value is new each run, no target can fake a pass by recognising it, and no report can fake a fail by inventing it.

    
The oracle does not ask the target what happened. It watches.

    
3. The oracle observes, it does not ask

    
A compromised target can say anything. So the oracle decides from facts it collects itself: every MCP frame on the wire, every file changed in the run's world, every request caught by the egress trap, which records calls and never forwards them.

    
The scenario declares which facts count as success, for example canary_leaked or egress_reached_sink. The verdict is simply whether those facts were observed.

    
Three verdicts, not two

    
exploited means the declared facts were seen. not_exploited means the run completed and they were not. inconclusive means the run did not complete, from a crash or a timeout, so the absence of findings proves nothing. A tool that reports a crash as a pass is a tool you cannot trust.

    
And a list of what it could not see

    
Every evidence file says which isolation tier ran and lists what could not be observed. An honest report includes its own blind spots, so the person reading it knows how far to trust it.

Defences21 Nov 20265 min read

  
A guardrail that blocks everything scores 100%. Here's how we stop that.

  
Gateways and guardrails for MCP are arriving fast. Buyers need to compare them, and builders need to know whether a change made theirs better. One number is not enough.

  

    
The one-number trap

    
Score a defence only on the attacks it blocks, and the winning strategy is to block everything. A guardrail that refuses every tool call stops every attack, and every useful task with it.

    
So Redfilade scores a defence on two numbers: the block rate, attacks stopped, and the false-positive rate, ordinary work wrongly blocked. A board can read both. A builder can set a threshold on both in CI.

    
How the score is measured

    
The defence runs as a container in its own cell, with no network. For every MCP message, Redfilade writes one line and the defence answers allow or block. Every attack and agent scenario then runs against its vulnerable twin with the defence in the path. Ordinary tasks, like looking up a customer or querying a name with an apostrophe in it, run against the secure twins.

    
A defence that crashes should not look like a defence that works.

    
Fail closed, on purpose

    
No answer within five seconds, a crash or a malformed line all count as a block. That can make a broken defence look strict, but the false-positive rate shows it: broken defences block ordinary work too.

    
Printing the uncertainty

    
Both numbers come with a Wilson 95% interval. That matters today, because the benign set is small: eight calls. A defence with zero false positives on eight calls could still have a true rate as high as about a third. We print that range rather than a reassuring zero, and the interval narrows as scenarios are added.

    
Using it as a gate

    
redfilade defend --min-block-rate 0.8 --max-false-positive-rate 0.05 fails the build if either number misses. Pick the thresholds that match the risk you carry, and keep the report as evidence of what the defence was tested against.

    
A defence-rules twin ships in the Range so you can see a pass and a fail before testing your own: the strict build stops path traversal, SQL injection, command injection and SSRF with no false positives; the permissive build stops nothing.
